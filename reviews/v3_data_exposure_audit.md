## Identity mapping and metadata exposure

GQA/VG names are not treated as proof of a new visual source. The primary [Visual Genome API documentation](https://visualgenome.org/api/v0/api_readme) defines `image_id`, `coco_id`, and `flickr_id`; the official [image metadata archive](https://visualgenome.org/static/data/dataset/image_data.json.zip) was not directly retrievable from the official host in this environment. The [Visual Genome Hugging Face mirror file](https://huggingface.co/datasets/jn12/VisualGenome/resolve/main/image_data.json.zip) was used after its SHA-256 (`b87a94918cb2ff4d952cf1dfeca0b9cf6cd6fd204c2f8704645653be1163681a`) matched the checksum listed in the official Visual Genome dataset-info metadata. The pinned record is `results/v3_final_validation/exposure/source/visual_genome_mapping_manifest.json`. Only `image_id -> coco_id` is used for image identity. It does not establish any COCO object/category label.

The mapping covers 100% of FineCops positive train and val GQA IDs. Train has 15,384 map rows carrying `coco_id` and 15,339 unique mapped COCO IDs (48.38% of the 31,795 images); val has 1,688 such rows and 1,687 unique mapped COCO IDs (47.32% of 3,567). The remaining records have a Visual Genome `image_id` row with an author-provided null `coco_id`; they are recorded separately from source IDs missing from the pinned VG archive. A null COCO field is not evidence of a non-COCO visual source or of historical non-exposure. An actual FineCops source ID absent from the pinned VG map is conservatively excluded and would block final acceptance if it entered a selected cohort. A second GQA ID can map to an already represented COCO ID, so collisions are explicitly handled rather than treated as unique photos. Before any pixel selection, both sides of the 9 train↔val shared mapped COCO IDs are removed. Within-split duplicate COCO mappings are also conservatively excluded (90 train IDs across 45 groups; 2 val IDs in one group). The official GQA image-ID sets themselves have zero train↔val overlap.

Full identity-pool intersections against historical COCO image pools before the cross-pool union are recorded in `results/v3_final_validation/exposure/source_identity_counts.json`: FineCops train maps onto 2,969 RefCOCO+ IDs and 3,877 RefCOCOg-UMD IDs; val maps onto 304 RefCOCO+ IDs and 359 RefCOCOg-UMD IDs. The overlap counts are not additive because historic pools overlap. All known historic COCO identities are unioned before eligibility is decided. Old FineCops positive test metadata has 4,313 GQA image IDs and 2,107 mapped COCO IDs; **all** old test identities are excluded from V3 eligible images, not only the old image-audit subset.

Current pre-pixel identity filters leave 27,110 metadata-eligible train images (4,685 excluded) and 3,110 metadata-eligible val images (457 excluded). Per-image reasons are in `identity_candidate_manifest.csv`, with a summary in `identity_audit.json`. These are candidate counts, not final audited cohorts.

GQA `train_sceneGraphs.json` and `val_sceneGraphs.json` contain 74,942 and 10,696 image IDs. Every FineCops positive train/val GQA ID is covered by one of the two graph metadata files (train: 31,666 in train and 129 in val; val: 3,546 in train and 21 in val). Both bulk files were already present locally and were loaded in prior/current metadata-audit work. The older FineCops feasibility audit loaded the complete val graph dictionary and queried old FineCops test IDs; this is recorded as annotation-metadata availability/use. It is not evidence that a V3 model was trained or reliability-scored on all those photos. The present identity audit read graph keys to quantify availability; it did not evaluate any grounding or reliability model. No claim is made that the source scene-graph annotations, photos, or images were unseen by any pretraining.

## Frozen pixel and perceptual audit rule

Before V3 confirmation scores, the audit rule was frozen in code as `v3-image-exposure-v1`:

1. Exact image identity: SHA-256 of EXIF-oriented decoded RGB pixels, prefixed by a version marker and little-endian width/height. JPEG byte hashes are retained for provenance but do not define visual identity.
2. Near-duplicate screen: grayscale horizontal 64-bit dHash, generated by Pillow after EXIF transpose, RGB conversion, 9×8 LANCZOS resize, and left-greater-than-right adjacent comparisons. Hamming distance **≤4** is a match.
3. Every match is a conservative exclusion. All historically available input photos are compared with selected new images; confirmation images are also compared with one another and with the selected development images. A within-confirmation near-duplicate cluster is excluded as a whole. If train and val pixels match, the candidate is excluded rather than allowed to cross the split.

This deterministic screen is not a proof that all semantic near-duplicates are found. Crops, substantial resizing, color/content edits, or dHash collisions/misses remain possible. Metadata mapping supplements, rather than replaces, actual pixel comparison. An unresolved or unreadable eligible image blocks the independent-confirmation label.

## Reproduction and outputs

Run from the repository root with the pinned environment:

```powershell
$env:PYTHONPATH = 'src'
$env:OPENBLAS_NUM_THREADS = '2'
$env:OMP_NUM_THREADS = '2'
& 'E:/conda/envs/deepminer/python.exe' scripts/v3_audit_exposure.py --stage all --workers 3 --hash-workers 4
```

The script stages are independently resumable: `metadata`, `identities`, `history`, `fetch-validation`, and `acquire`. It writes no old files. Source identities/counts, mappings, the row-level historical identity registry and image fingerprints, individual download reports, per-image candidate decisions, the positive-box audit, per-expression JSONL cohorts, acquisition-attempt log, and acceptance status are under `results/v3_final_validation/exposure/` (official annotations and new image bytes are only under `data/raw/v3_finecops/`). `tests/test_v3_exposure.py` checks decoded-pixel identity, dimensions, exact dHash Hamming-radius matching, positive-intersection bbox handling, and streamed JSON parsing. These tests validate the implementation; the actual full-image audit and annotation report establish the recorded result.
